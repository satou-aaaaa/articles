データ移行はソフトウェア開発における大きな課題のひとつです。
UIの表示を変更することはあってもデータ構造を変更することはほとんどありません。
特にひとつのテーブルに大量のカラムが存在しているような場合、データ構造を変更したときの影響範囲が広すぎてしまう可能性があります。
そのため変更しづらいデータ構造はそのままにされてしまいます。
ただし、それをずっと無視できる訳ではありません。
様々な理由(サポートの終了、ユーザビリティの向上等)から、データを新しいアプリケーションに移行させなければいけない時が必ずやってきます。
つまり、私たちは安全なデータ移行ができるように常に注意しなければいけません。

ここで安心してほしいのが、前述されている手法を用いていればデータ移行はシンプルで安全に行うことができます。

```kotlin
fun migration(){
	val oldData = oldRepository.resolveAll()

	val newData = this.convertToNewData(oldData)

	newRepository.add(newData)
}

fun convertToNewData(oldData:OldData):NewData{
	// 変換処理を行う
}
```

古いデータ構造と新しいデータ構造が同じであれば変換処理すら不要です。
変換が必要な場合でもテストコードが書きやすいのでよりミスしづらくなっています。
データ移行の対象は小さければ小さいほど安全です。

```kotlin
fun migration(){
	val oldData = oldDaoFacade.selectAll()

	val newData = this.convertToNewData(oldData)

	newDaoFacade.insert(newData)
}
```

```kotlin
fun migration(){
	val oldData = oldDao.selectAll()

	val newData = this.convertToNewData(oldData)

	newDao.insert(newData)
}
```

上記の方法では一旦同じデータベースに変換後のデータ構造を生成し、そこからデータをexport、importし新しいデータベースに移行します。
このように、データの変換とデータの移動は別で行ったほうがより安全です。

## 危険なデータ移行
ここまで説明していたデータ移行手法は実質的に実行不可能です。
何故なら、古いデータ構造は悪い構造になっていることが多いからです。
長年運用されたデータベースにはinteger型にnullが入っていることもあります。(integer型はデフォルトで0になることが多いので、nullは異常値)
データ移行を決心する理由も既存のデータ構造が原因になっていることがほとんどです。
そもそもDDDやTDDが発明される前から存在しているデータ構造もあります。
つまり、前述したようなoldRepositoryからデータを抽出する方法は無いと考えたほうが良いです。(運が良ければRepositoryのようなものがあるかもしれませんが、当てにしないほうが良いでしょう)
このようなことから、データ移行は本質的に複雑で危険です。

## 大規模なデータ移行
ただでさえ複雑で危険なデータ移行を大規模で行おうとした場合、データが破損することを前提にしなければいけません。
ですが、データの破損は看過されないことが多く、現実的ではありません。
つまり、大規模なデータ移行はデータを壊すか、臭い物に蓋をするしかありません。
大規模なデータの変換と移行を同時に行うSQLの作成は絶対にやらないでください。自殺行為です。
では、大規模なデータ移行をしたい時はどうすれば良いでしょうか。

## コアなデータのみ移行する
大規模なデータを全て移行するのは実質的にほぼ無理なため、対象のデータを絞る必要があります。
コアなデータとは、アカウントを認証するのに必要なデータを指しています。
- メールアドレス
- 電話番号

等

これらのデータのみ移行し、新しいアプリケーションで改めて登録してもらいます。
idも新しいアプリケーションで発行したほうが良いでしょう。
もし古いアプリケーションのデータが見たくなったら古いアプリケーションにアクセスしてもらいます。
古いアプリケーションは数年間は使えるようにしておくか、または即停止し新しいアプリケーションしか使えないようにします。(この場合古いデータは見れなくなります)
新しいアプリケーションから古いアプリケーションに問い合わせる仕組みを導入することも考えられますがおすすめしません。
古いアプリケーションにはいくつかの問題があります。
- 使っているプロトコルが古く、サポートが切れている
- 使っているOSが古く、セキュリティ上の問題がある
- テストが書かれていないため、本当に欲しいデータなのかどうかがわからない

このような理由から、古いアプリケーションに問い合わせるのは複雑で危険です。

## まとめ
古いデータ構造と戦わないようにしましょう。負け戦をする必要はありません。
コアなデータのみ移行するか、臭い物に蓋(腐敗防止層)をするかを選びましょう。
新しいデータ構造は捨てやすい構造にしましょう。(前述の手法を用いていれば問題ありません)
